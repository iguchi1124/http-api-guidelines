# HTTP API開発ガイドライン

更新日: 2026-11-25

## 1. 適用範囲

HTTP APIの設計、実装、OpenAPIによる仕様管理、および変更レビューに適用する。
本文の採用方針と参照仕様の適用可能な要件に従う。末尾の「未決定事項」は必須ルールではなく、プロジェクトごとに決める事項である。

## 2. 採用するツール・仕様

| 分類 | 採用方針 |
| --- | --- |
| バージョン管理 | Git |
| コミット規約 | Conventional Commits 1.0.0 |
| HTTPの意味と振る舞い | RFC 9110 |
| HTTPを利用したAPI設計 | RFC 9205 |
| QUERYメソッド | RFC 10008 |
| エラー詳細 | RFC 9457 |
| API仕様の記述 | OpenAPI Specification 3.2以上 |
| JSONペイロード | application/jsonを基本とし、オブジェクトは原則として用途別のルートキーで包む |

ペイロードは本書の共通方針と各エンドポイントのOpenAPI定義に従う。JSON:APIは採用しない。エラー詳細にはRFC 9457を採用する。

## 3. Gitとコミット

ソースコード、OpenAPIドキュメント、関連ドキュメントをGitで管理する。
コミットメッセージは[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)に従う。

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

- 新機能には`feat`、不具合修正には`fix`を使用する。
- 破壊的変更は`!`または`BREAKING CHANGE:`フッターで示す。
- その他の変更には`docs`、`refactor`、`test`、`ci`など適切なタイプを使用できる。

```text
feat(orders): 注文キャンセルAPIを追加
fix(auth): 期限切れトークンの判定を修正
docs(api): レスポンスの説明を更新
```

## 4. リソース指向のAPI設計

RESTfulなリソース指向設計を基本とする。取得、一覧、作成、更新、削除は、リソースを表すURLとHTTPメソッドの意味に従って表現する。

HTTPメソッドの安全性・冪等性、ステータスコード、ヘッダー、メディアタイプ、コンテントネゴシエーションなどは[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)に従う。HTTPを利用した設計は[RFC 9205](https://www.rfc-editor.org/rfc/rfc9205.html)に従い、既存のHTTPの意味を独自に変更しない。

### 4.1. カスタムアクション

標準操作では自然に表現しにくい業務操作には、`POST`または`QUERY`によるカスタムアクションを許容する。操作名だけでなく、要求する処理の意味に応じてメソッドを選ぶ。

| メソッド | 用途 | 例 |
| --- | --- | --- |
| `POST` | 状態変更を伴う操作など、安全な照会として扱えない処理 | 注文のキャンセル、検証済み状態の確定 |
| `QUERY` | リクエスト本文で条件や入力を渡す、安全かつ冪等な照会・計算 | 状態変更を要求しない注文内容のプレビュー |

`QUERY`の意味は[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008.html)に従う。ここでの`QUERY`はHTTPメソッドを指す。

```http
POST /orders/{orderId}/cancel
POST /email-verifications/{verificationId}/verify
QUERY /orders/{orderId}/preview
```

- 特定リソースの操作は`POST /{resources}/{resourceId}/{action}`または`QUERY /{resources}/{resourceId}/{action}`とする。
- `action`には`cancel`、`verify`、`preview`など、業務上の意図が明確な短い動詞を使用する。
- 通常のCRUDを`get`、`create`、`update`、`delete`などのアクションとして定義し直さない。
- クライアントが状態変更を要求する操作には`GET`や`QUERY`を使用しない。例えば、`verify`が検証済み状態を保存したりトークンを消費したりする場合は`POST`を使用する。
- `QUERY`は安全かつ冪等であることを保証する。アクセスログなどの付随的な処理は安全性と区別する。冪等性は、時間経過や対象データの変化にかかわらず同じレスポンスを返すという意味ではない。
- 実行可能な状態、実行後の状態、副作用、入力、出力、エラーをOpenAPIで定義する。
- 再実行時の振る舞いを定義する。POSTであることから冪等性や安全な再試行を推定しない。
- 操作自体の履歴や処理状態を管理する必要がある場合は、独立したリソースとしての表現も検討する。

標準操作を優先する考え方は[Google AIP-136](https://google.aip.dev/136)を参考にする。URLはGoogleのコロン形式ではなく、上記のスラッシュ形式を採用する。同形式の実例には[Microsoft Graphのevent: cancel](https://learn.microsoft.com/en-us/graph/api/event-cancel?view=graph-rest-1.0)がある。

## 5. JSONペイロード

リクエストおよび正常系レスポンスのJSONペイロードには、原則として`application/json`を使用する。ファイル配信や専用メディアタイプが必要な表現は、エンドポイントごとに定義する。

### 5.1. ルートキー

- JSONオブジェクトを送受信する場合、原則として実データをルートキーで包む。
- ルートキー名は、リソースや操作の用途に応じてエンドポイントごとに任意に命名できる。`data`など特定の共通名には固定しない。
- アプリケーションが定義するJSONキーは、ルートキー・入れ子のフィールド・付加情報・Problem Detailsの拡張メンバーを含め、`snake_case`に統一する。小文字の英単語をアンダースコアで区切る（例: `user_profile`、`display_name`、`next_cursor`）。
- この命名規則はリクエストとレスポンスの両方に適用する。OpenAPIなど外部仕様が定義する固定のキー名は、その仕様に従う。
- 任意とは設計時に選択できるという意味であり、リクエストやレスポンスのたびに変更できるという意味ではない。名前と構造はOpenAPIで固定する。
- この規約はペイロードの最上位のラップに適用する。入れ子のオブジェクトすべてに追加のラッパーを要求するものではない。
- 原則から外れる表現を採用する場合は、理由と構造をOpenAPIに明記する。

単一リソースのレスポンス例:

```json
{
  "order": {
    "id": "ord_123",
    "status": "confirmed"
  }
}
```

別のルートキーを使用する例:

```json
{
  "user_profile": {
    "display_name": "Example User"
  }
}
```

例中の`order`や`user_profile`は固定名ではない。識別子の型、属性名、関連データの構造は各APIで定義する。

### 5.2. 一覧・関連データ・付加情報

一覧も原則としてトップレベルのオブジェクト内に名前付きの配列を配置する。配列のキーは用途に応じて命名し、0件の場合は空配列で表す。

```json
{
  "orders": [
    {
      "id": "ord_123",
      "status": "confirmed"
    }
  ]
}
```

0件の一覧の例:

```json
{
  "orders": []
}
```

通常のID指定取得で対象が存在しない場合は404とし、一覧が0件の場合と区別する。

ページング情報、関連データ、リンク、付加情報の有無・配置・名前はOpenAPIで定義する。共通の`links`や`meta`キーを必須としない。ページング方式やリンク名も本書では固定しない。

### 5.3. 作成・更新・カスタムアクション

- 入力と結果のルートキー、各フィールドの型・必須性・意味をOpenAPIで定義する。
- 入力と出力のルートキーはそれぞれの用途に応じて決める。
- 更新では、HTTPメソッドと採用するメディアタイプに沿って、省略されたフィールドとnullの意味を定義する。
- `POST`・`QUERY`いずれのカスタムアクションも、オブジェクトを返す場合は原則としてルートキーで包む。結果が更新済みリソースか操作固有の結果かを明記する。

キャンセル完了後に更新済みリソースを返す例:

```json
{
  "order": {
    "id": "ord_123",
    "status": "cancelled"
  }
}
```

### 5.4. 本文を返さない場合・非同期処理

204 No ContentやHEADへのレスポンスには本文を付与しない。空のJSONオブジェクトや`null`も送信しない。202 Acceptedは受付済みであり処理完了を意味しない。非同期処理を採用する場合は、状態確認方法と完了・失敗時の表現をOpenAPIに定義する。[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3)

## 6. エラー詳細

本文を返せるエラーレスポンスの詳細は[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)に従い、`application/problem+json`で返す。Problem Detailsオブジェクトをトップレベルに置き、正常系のルートキーによるラップ規約は適用しない。

| メンバー | 意味 |
| --- | --- |
| `type` | 問題の種類を識別するURI参照。省略時は`about:blank` |
| `title` | 問題の種類を表す短い説明 |
| `status` | 発生した問題に対して生成したHTTPステータスコード |
| `detail` | 個別の問題発生に関する説明 |
| `instance` | 個別の問題発生を識別するURI参照 |

全メンバーを一律に必須とはしない。`status`を含める場合は生成するHTTPレスポンスのステータスコードと一致させる。機械的な判定は`type`や定義済みの拡張メンバーを使用し、`detail`の文章解析に依存しない。機密情報や不要な内部実装情報をエラー本文に含めない。

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.example.com/problems/order-not-cancellable",
  "title": "Order cannot be cancelled",
  "status": 409,
  "detail": "発送済みの注文はキャンセルできません。"
}
```

このURLは説明用であり、実際の問題タイプはサービスが管理する識別子として定義する。

## 7. OpenAPIによる仕様管理

[OpenAPI Specification 3.2以上](https://spec.openapis.org/oas/v3.2.0.html)を採用する。

- `openapi`フィールドに使用する具体的な仕様バージョンを記載する。`info.version`と混同しない。
- エンドポイント、HTTPメソッド、認証要件、パラメーター、本文、ステータスコードを記述する。
- `QUERY`は[Path Item Objectの`query`フィールド](https://spec.openapis.org/oas/v3.2.0.html#path-item-object)に定義し、入力本文は`requestBody`で記述する。URLのクエリパラメーターを表す`in: query`とは区別する。
- 正常系の`application/json`とエラー系の`application/problem+json`を、それぞれのレスポンスの`content`に定義する。
- 選択したルートキーとラッパー構造を含め、フィールドの型、必須性、null許容、列挙値、実例を記述する。ルートキー名の変更は互換性への影響を評価する。
- `links`を一律に`required`へ追加しない。個別要件で必須化する場合はその理由を明記する。
- 実装変更とともに仕様も更新する。使用する検証・コード生成ツールが採用バージョンを扱えることを確認する。

## 8. 未決定事項

以下は共通方針として未決定である。既存のプロジェクト規約があれば従い、新たに決める場合は判断理由とともに記録する。以下の候補や本文の例を、無条件の必須ルールとして扱わない。

| 論点 | 決める内容 |
| --- | --- |
| アクション命名 | 複数語のアクション名のURL上の表記 |
| ページング | カーソルかオフセットか、パラメーター、上限、最終ページの表現 |
| 総件数 | 提供の有無、正確値か概算か、絞り込みとの関係 |
| 型と値の表現 | 識別子、日時、金額、数値精度、列挙値 |
| nullと省略 | 任意属性が欠ける条件、未設定値の意味、採用する更新形式に応じた省略規則 |
| 関連と同梱 | 関連データの埋め込み・参照方法、提供範囲、深さ、フィールド選択 |
| カスタムアクション | 入力のメディアタイプ、結果、再実行時の扱い、非同期処理 |
| APIの互換性 | 公開バージョン方式、非推奨化、移行期間、列挙値追加の扱い |

## 9. エージェントへの適用

設計・実装・レビューでは、確定した採用方針と未決定事項を区別する。既存APIへ適用するときは互換性への影響を確認し、依頼範囲外の一括変更を行わない。

共有ルールを変更するときは、AGENTS.mdとCLAUDE.mdの同等の指示を可能な限り整合させ、それぞれのツール固有の指示は保持する。
